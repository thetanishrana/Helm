# Helm: live oversight for AI browser agents

*A research prototype. Every number below comes from small, author-written or LLM-written test sets and one local agent unless stated otherwise; read the limits section before quoting anything.*

## The problem
AI agents that browse the web read page text they cannot fully trust. A page can contain text written to look like the user, the system or the site owner ("also click Forward all mail"), and an agent may act on it. Today a person supervising the agent sees either a raw log or a generic "Allow this action?" prompt, which people click through. Helm tries a narrower thing: stay quiet when the user asked for the action, and when the agent does something the user did not ask for, say so and say which page text pushed it, **before** the action runs.

## What I built
Two proxies sit underneath the agent, so Helm is not tied to one agent product:
- a **model tap** on the LLM API (base-URL override) that sees each tool call the model wants to make and which untrusted page content was in its context;
- a **browser tap** on the Chrome DevTools Protocol that sees the resulting browser actions.

A rule-based policy classifies each action, and an explainer decides whether the user asked for it, how consequential it is, and which page passage most plausibly pushed the agent. Risky, unrequested actions are **held** (the stream is kept alive with SSE pings) until the person decides in a local web UI; "deny" ends the turn with a text block instead of faking errors, which agents otherwise retry around. An optional counterfactual check re-runs the model without the suspect passage. Three later additions:
- an **attribution judge** (on by default, `--no-judge` to disable): when the heuristics cannot name the cause, a Claude model reads the numbered page passages and returns the number of the one that asks the agent to take exactly this action, or none. It runs while the card is already waiting, so it adds no delay, and the card then says "A model reading the page judged that this text ... pushed the agent". It sends page text and the person's request to Claude, so it is for the owner's own runs, never for study participants;
- a **read-only lookup of CSS selectors** on the live page, so a click on `#btn-3` is judged by the control's real label instead of being paused as unreadable;
- **several agents in one interface** (`node src/cli.mjs fleet <file>`): a fleet strip, one course lane per agent, agent-named decision cards and a receipt per agent. Agents must use separate browser sessions, or Helm cannot tell their actions apart (seen live).
Stack: Node 24, no build step, 144 tests that run in a few seconds with no network, plus 33 interface checks driven in Chrome.

## What it got wrong (the useful part)
Testing on attacks I did not write found real gaps, and I kept the record instead of tuning it away:
1. **Dev numbers overstated generalisation, and every fix round did too.** 12/12 on pages the explainer was built from became 5/8 on unseen ones; after fixing, a new author's set still let 3 of 12 through ("Cancel booking", "Unlock front door", "Change direct deposit…"), and after fixing those, the next author's set let through "Disable firewall". The risk list was a vocabulary; every author found a verb it lacked. I replaced it with an allowlist of harmless button words (an unknown button is consequential), which a fifth blind set with mild labels (Release, Disarm, Bypass...) did not get past, at the cost of a pause on an unfamiliar harmless button ("View document"). The misses were "Cancel all…", "Turn off MFA…" and "Make … public" buttons missing from the consequential-verb list, plus injections posing as the user, an owner or an identity provider. I fixed those, which turned the first set into dev data; the second, fresh set is the clean figure.
2. **Helm was better at stopping than at explaining.** Interception is largely driven by a risk rule (an unrequested click on anything not known to be harmless pauses whatever the page says). Naming the page text that caused the action worked on 3 to 4 of 12 attacks in the clean sets, because injections that describe the button instead of repeating its words share few words with it. (An earlier "2 of 12" was partly my measurement: the offline detector could not see text revealed by a click. I corrected it and say so in `docs/heldout-findings.md`.) A hand-written paraphrase lexicon did not help on a clean set. A language-model judge did (see the table), but its first run on a truly fresh set was a null result caused by my own extraction bugs, and the judge can attach a plausible cause to a harmless false pause (it did on 2 of the first 3), which is the one way it can mislead a person.
3. **Text in attributes was a weak spot.** An instruction in an image's alt/title text was missed offline and let a real attack through live (the agent chained a click on "Refill all prescriptions and ship", and no word in the risk list matched). The allowlist closed the interception side. The explaining side was still blind to long aria-labels until the sixth set exposed the parser bug above; that is fixed.
4. **It can pause harmless steps it cannot read.** Clicks made with CSS selectors or `eval` snippets showed up as an unnamed target, and Helm paused them as the safe default. CSS selectors are now looked up on the live page (checked against a real Chrome, not yet measured on the evaluation sets); `eval` snippets are still opaque. The allowlist also pauses some unfamiliar harmless buttons (7 of 65 harmless actions across the last four sets, 4 of 23 on a batch built to provoke it: "View refill history", "Show payment schedule", "Print order summary"; a later read-only-label fix removed them offline, 0 of 89 on sets 5-9, in-sample, and a red-team on a fresh batch then found two disguised consequential buttons it let through, which a tightening closed, also in-sample).
5. **A user-requested "Send" button in a chat box was paused** as an unrequested send.

## The interface
A local web page beside the browser (`docs/assets/ui-attributed.png`; dark, narrow and several-agent variants alongside). The person's request is the destination; the agent's steps are marks on a course; an action outside the request leaves the course in red and waits. The decision says what was asked and what the agent wants, in plain words, quotes the page text that pushed it, says how risky it is, and reports whether re-running the agent without that text removed the action. Approving a high-risk action means pressing and holding. It is designed to be quiet when the person asked for the step. With several agents it adds a strip of one chip per agent (the waiting one marked), a single queue of decisions each naming its agent and that agent's request, and one course lane per agent. It ships with a strict content-security-policy, bundled fonts, light and dark modes, keyboard operation and reduced-motion support, and an automated check that drives it in Chrome. It has not been tried with a person: the wording, the hold-to-confirm friction and the framing are hypotheses for the pilot to test.

## What I did not do
- **No user study.** I had no participant pool, so the human-factors claim (that explanations help people decide) is a design hypothesis, not a result. An instrument for a qualitative pilot exists (`src/replay/`) and has only been tested with simulated participants.
- **No activation-level detection** (reading model internals for task drift). It was the first thing cut.
- **No test of the judge on human-written attacks, or with a judge model other than Claude Haiku 5.5.**
- **No claim about strong agents.** The one stock Claude agent I ran followed none of the injections, so the protection claim rests on a susceptible local model, which gives an upper bound on susceptibility.

## Limits to keep in mind
Test pages were written by me or by LLMs (ChatGPT and fresh Claude sessions), not by human attackers; each held-out set has one author and 6-12 attack pages, so the confidence intervals are wide; the offline detector sees the page snapshots, not a live agent; live-agent runs are unseeded, 1-2 repetitions per page, and the protected and unprotected batches are separate samples, not paired runs. Several fixes were made after seeing a set, which turns that set into dev data; the table says which figures are clean and which are in-sample, and the clean test of the final judge is one set of 6 attack pages.

The honest summary: Helm usually stops the consequential click on pages it has not seen (the allowlist version intercepted 24 of 24 across the last three sets), at the price of false pauses on harmless controls with a serious-sounding word in the label (7 of 65 harmless actions; 4 of 23 on a batch built to provoke them), which a later read-only-label fix removes (0 of 89 in-sample, 0 of 24 on a fresh batch). That fix briefly let two disguised consequential buttons through a red-team (6/8 interception on that batch) until it was tightened; any label-based rule can be steered by a page that controls its labels. The part that used to be weak, saying which page text pushed the agent, went from about a third to every one of 24 attack pages once a language-model judge was added, and that judge sends page text to Claude by default and can still attach a cause to a harmless false pause (1 of 4 on the last fresh batch). The evidence that any of this helps real supervisors does not exist yet: no person has used it.
